How the cache works

Why your usage breakdown is mostly cache reads, what makes a prefix reusable, how long it survives, and what silently breaks it.

Two different things get called "the cache", and keeping them apart is most of the battle:

KV cachePrompt caching
What it isKeys and values held in GPU memory while a single request runsPrefix state kept between requests so it can be reused
LifetimeThe request5 minutes, or 1 hour if you pay for it
You control it?No — always on, invisibleYes — via cache_control breakpoints

They rest on the same mechanism, which is why the naming collides. This document covers the mechanism once, then spends most of its length on the second one, since that's the one on your invoice.

Prefill and decode

Serving a request splits into two phases with completely different performance characteristics.

Prefill processes your entire prompt in one shot. All tokens go through all layers in parallel — big matrix multiplies, the GPU saturated, compute-bound. Every token's Key and Value vector at every layer gets computed and held in memory. This is what you wait for before the first token appears.

Decode then emits one token at a time. Each new token computes its own Q, K and V, attends over every cached K/V from before, and appends its own. One token wide, so the matrix multiplies are thin and the GPU spends most of its time waiting on memory bandwidth rather than computing. This phase is memory-bound, and it's why output tokens cost roughly five times input tokens.

Why a prefix can be reused

Here's the load-bearing fact, and it comes straight from the causal mask in the first document:

Token i's Key and Value vectors depend only on tokens 1 through i. Nothing that comes later can change them, because attention at position i cannot see past it.

So if two requests begin with byte-identical text, the K/V state for that shared span is identical too — not similar, identical. It can be computed once and reused. The expensive prefill for that span never has to run again.

Three consequences fall straight out of this, and between them they explain almost every caching surprise:

  • It's a prefix cache, not a content cache. Reuse only works from the start of the prompt forward, up to the first difference. A cached paragraph that appears in the middle of an otherwise-different prompt buys you nothing.
  • One token of difference kills everything after it. Change token 40 of a 50,000-token prompt and tokens 41 onward must be recomputed. A timestamp near the top of a system prompt costs you the entire cache.
  • Order is the whole design. Static content first, volatile content last. The request is assembled as tools → system → messages, in that order, and that's the order the hierarchy invalidates in.

Breakpoints and the lookback window

Reuse doesn't happen for free — the API only writes a cache entry where you tell it to. That marker is cache_control, and it goes on a content block:

system=[
    {"type": "text", "text": WHOLE_STYLE_GUIDE,
     "cache_control": {"type": "ephemeral"}},
]

Three rules govern what happens next, and getting them wrong is the usual cause of "I enabled caching and nothing changed":

  1. Writes happen only at your breakpoint. Marking a block writes exactly one entry — a hash of the entire prefix ending at that block. No entries are written at any earlier position.
  2. Reads look backward for entries a previous request wrote. The API hashes the prefix at your breakpoint; if there's no match it walks back one block at a time looking for a hash that some earlier request already stored. It is hunting for prior writes, not for stable-looking content.
  3. The lookback window is 20 blocks. If no match turns up within 20 positions, it stops.

Rule 2 is the one that catches people. Consider a prompt with a large static system context in blocks 1–5 and a per-request block 6 containing a timestamp and the user's message, with the breakpoint on block 6:

request 1  hash(1..6) written             ← includes the timestamp
request 2  hash(1..6) differs → no match
           walk back: 5, 4, 3, 2, 1 — nothing was ever written there
           result: full-price prefill, plus another useless write

You pay the 25% write premium on every single request and never once get a read. The lookback cannot rescue you, because it only finds entries that earlier requests wrote, and writes only happen at breakpoints. Move cache_control to block 5 — the last block that's identical across requests — and every subsequent request hits.

You get up to four breakpoints. A second reason to use more than one: in a long conversation each turn appends blocks, and once your breakpoint drifts 20 or more blocks past the last write, the window misses it. An extra breakpoint further back gives the lookback something to find.

Breakpoints are free. Adding them doesn't cost anything by itself. You're billed on tokens written and tokens read, not on the number of markers. There's no reason to be stingy with the four you get.

Or let the API place it for you

For a straightforward growing conversation, put cache_control at the top level of the request and the breakpoint moves forward on its own as turns accumulate:

response = client.messages.create(
    model="claude-opus-5",
    max_tokens=1024,
    cache_control={"type": "ephemeral"},   # automatic
    system=SYSTEM_PROMPT,
    messages=history,
)

It places the breakpoint on the last cacheable block, so it walks into exactly the same trap as above when your last block is the one that varies. For a plain chat transcript it's the right default; for a prompt with a volatile tail, use an explicit breakpoint at the end of the static prefix instead.

How long it lives

Five minutes by default. Reading the entry refreshes it at no charge, so an active session stays warm indefinitely without ever paying a second write. The clock starts when the request that touches the entry begins, not when its response finishes — so a four-minute streaming response leaves roughly one minute of usable life after it completes.

When the hour is worth buying

The 1-hour TTL is an explicit opt-in and costs double base input on the write:

"cache_control": {"type": "ephemeral", "ttl": "1h"}

The break-even arithmetic is simple. A 5-minute write carries a 0.25× premium and each read saves 0.9×, so one read pays it back. A 1-hour write carries a 1.0× premium, so it needs two reads before it's ahead. If your traffic is more frequent than every five minutes, the standard cache refreshes for free and the hour buys you nothing. It earns its keep when gaps land in the awkward zone — longer than five minutes, shorter than an hour. A side-agent that runs for eight minutes, or a user who takes a coffee break mid-conversation.

If you mix TTLs in one request, the longer one has to come first: all 1-hour breakpoints before any 5-minute breakpoints.

What this costs

Reading your usage numbers

The response reports three separate input counts, and the one named input_tokens is not your total. It's only the tokens after the last breakpoint.

total_input = cache_read_input_tokens
            + cache_creation_input_tokens
            + input_tokens
The diagnostic that answers most questions. If cache_creation_input_tokens and cache_read_input_tokens are both zero, no caching happened at all — and no error was raised. The usual causes are a prompt below the minimum cacheable length, a missing or stripped cache_control field, or a proxy in front of the API that dropped it. If you reach the API through a gateway or corporate proxy, this pair of fields is the cheapest way to confirm the breakpoint survived the trip: fire the same request twice in quick succession and check whether the second one reads.

Minimum cacheable length

Below the threshold, cache_control is silently ignored. No error, no caching, no clue unless you check the usage fields.

What breaks it

Invalidation follows the tools → system → messages hierarchy: a change at one level invalidates that level and everything after it.

and the non-obvious ones

  • Unstable JSON key ordering. Some languages randomise map iteration order when serialising. If your tool_use blocks come out with keys in a different order each time, the bytes differ and the cache misses every request. Go and Swift are the usual offenders.
  • Anything derived from the clock. A date, a request ID, a session token near the top of a system prompt. Move it to the end or drop it.
  • Concurrency. An entry only becomes available once the first response has begun. Fire ten parallel requests with the same new prefix and you'll pay ten writes. Let the first one land, then fan out.
  • Isolation boundaries. Caches never cross organisations. On the Claude API they're also isolated per workspace; Bedrock and Google Cloud isolate at the organisation level only. If you split traffic across workspaces, you split your cache too.

Warming it before you need it

If the first user request of the day shouldn't eat the cold-prefill latency, you can pay for the write in advance with max_tokens: 0. The API reads the prompt, writes the entry, and returns immediately with an empty content array and no output tokens billed.

client.messages.create(
    model="claude-opus-5",
    max_tokens=0,
    system=[{"type": "text", "text": SYSTEM_PROMPT,
             "cache_control": {"type": "ephemeral"}}],
    messages=[{"role": "user", "content": "warmup"}],
)

Put the breakpoint on the shared prefix, not on the placeholder message — otherwise the entry is keyed to the placeholder and your real traffic won't hit it. Automatic caching is wrong here for exactly that reason. Match the thinking and effort settings to your real requests too, since those get rendered into the prompt. And the TTL still applies: keep re-warming inside the window, or buy the hour.

Checklist

  1. Order the prompt tools → system → static context → volatile content. Nothing time-varying above the breakpoint.
  2. Put cache_control on the last block that is byte-identical across the requests meant to share a cache.
  3. Confirm the cached region clears your model's minimum length.
  4. Check cache_read_input_tokens on the second request. Both counters zero means caching never engaged.
  5. Keep tool_choice, image presence, thinking config and effort constant across calls in a session.
  6. Reach for the 1-hour TTL only when gaps genuinely exceed five minutes but stay under an hour.
  7. Add a second breakpoint further back when a conversation grows more than 20 blocks past the last write.
  8. Let the first request of a new prefix complete before fanning out in parallel.
